## Находки

### TD-1. Порт терминала не закреплён на время proxy-запроса

- **Файлы:** `app/ttydproxy/manager.py:36-54,193-202,222-236`,
  `app/ttydproxy/app.py:477-503`
- **Риск / трудоёмкость:** высокий / L
- **Факт:** `get_terminal()` возвращает только снимок `id`/`port` и отпускает
  lock. После этого `delete_terminal()` может освободить порт, а
  `_allocate_port()` немедленно выдаёт наименьший свободный порт новому
  терминалу. HTTP/WS connect выполняется позже по сохранённому номеру порта.
- **Последствие:** узкое конкурентное окно позволяет запросу к удалённому
  терминалу подключиться к уже созданному терминалу. Долг уже отмечен комментариями
  в коде, но отдельного lease/refcount-контракта и детерминированного теста гонки
  нет.
- **Рекомендация:** добавить lease на terminal generation до завершения connect
  (либо не переиспользовать порт до освобождения lease). Начать с теста, который
  ставит barrier между lookup и connect, затем удаляет и пересоздаёт терминал.

### TD-2. Security-чувствительные SSH-проверки всё ещё имеют local/remote копии

- **Файл:** `bin/clihost-sync.sh:132-217,414-510`
- **Риск / трудоёмкость:** высокий / M
- **Факт:** после вынесения remote symlink guards в `emit_remote_prelude()` в
  скрипте остаются две реализации `path_mode`, `reject_control_chars`,
  `reject_group_or_other_permissions`, `is_private_key_file`,
  `validate_default_public_ssh_material`, `validate_private_key_permissions` и
  `private_key_include_rule`. Одна работает локально, вторая текстом отправляется
  через SSH.
- **Последствие:** исправление распознавания ключей, прав или управляющих
  символов может попасть только в одну сторону sync. Это особенно рискованно для
  `--include-private-keys`, где расхождение меняет security boundary.
- **Рекомендация:** генерировать общий prelude со всеми чистыми валидаторами и
  использовать его локально и в remote payload; оставить раздельными только I/O
  orchestration-функции. Добавить contract-тест на эквивалентные local/remote
  verdicts, а не только проверки текста скрипта.

### TD-3. `entrypoint.sh` одновременно bootstrap, launcher и частичный supervisor

- **Файл:** `entrypoint.sh:224-586` (особенно `277-354`, `365-449`, `454-586`)
- **Риск / трудоёмкость:** высокий / L
- **Факт:** 586-строчный entrypoint последовательно настраивает home/sshd,
  обновляет Hermes, регистрирует Droid, запускает Droid/ao/tunnel/proxy/hapi,
  строит URL и затем `exec`-ит sshd. Блоки запуска повторяют подготовку log-файла,
  `chown`, background launch, сохранение PID и разные варианты ошибки.
  После печати PID процессы Droid, ao, tunnel, proxy и hapi не проверяются и не
  перезапускаются; жизнеспособность контейнера определяется только sshd.
- **Последствие:** добавление ещё одного сервиса увеличивает разнобой fail-fast /
  warn-and-skip и риск «контейнер running, функция недоступна». Тесты вынуждены
  исполнять или анализировать весь entrypoint вместо небольших контрактов.
- **Рекомендация:** сначала зафиксировать матрицу обязательности сервисов и
  ожидаемое поведение при их смерти. Затем вынести `configure_*`, единый
  `start_background_service` и readiness/liveness-проверки; полноценный
  supervisor вводить только отдельным решением, не как побочный рефакторинг.

### TD-4. Runtime env-переменные парсятся по разным правилам

- **Файлы:** `app/ttydproxy/security.py:17-63`,
  `app/ttydproxy/config.py:8-35`, `entrypoint.sh:278,328,365,459-468,557`
- **Риск / трудоёмкость:** средний / M
- **Факт:** Python принимает для boolean `1/true/yes/on` и при неизвестном
  значении молча берёт default; Bash-сервисы включаются только при точном
  `"true"`, поэтому `TRUE`/`1` означают «выключено». Числа в Python обычно
  откатываются к default или clamp-ятся, тогда как Bash для части портов завершает
  startup. Единого списка переменных и политики fail-open/fail-closed нет.
- **Последствие:** одинаково выглядящая конфигурация даёт разные результаты для
  web proxy и фоновых сервисов, а опечатка в enable-флаге выглядит как штатное
  отключение.
- **Рекомендация:** описать контракт для boolean/integer/secret и применить общие
  Bash helpers до запуска процессов; для enable-флагов предпочесть явную ошибку
  на неизвестном значении. Добавить table-driven тесты на одинаковый набор
  входов.

### TD-5. Импорт `ttydproxy.app` создаёт production state, а handler объединяет все features

- **Файл:** `app/ttydproxy/app.py:47-69,87-503`
- **Тесты:** `tests/unit/handler_stubs.py:1-21`,
  `tests/integration/test_ttyd_handler.py:1-28`
- **Риск / трудоёмкость:** средний / M
- **Факт:** manager, два rate limiter и availability-флаг создаются как module
  globals при импорте. Один `TTYDProxyHandler` содержит routing, auth/CSRF,
  parsing, login, cleanup, upload, terminal lifecycle и proxy dispatch. Общий
  test stub подменяет auth/CSRF, а файл с названием integration тестирует только
  чистую функцию `resolve_vkbd_enabled`, не HTTP boundary.
- **Последствие:** тесты зависят от monkeypatch глобалов и легко пропускают связку
  route → auth/CSRF → handler. Параллельные тесты или несколько server instances
  делят mutable state.
- **Рекомендация:** ввести `create_app(settings, manager, limiters)`/контекст
  зависимостей и тонкий route dispatcher. Сначала добавить socket-level тесты
  критичных auth/CSRF маршрутов на реальном handler, затем декомпозировать.

### TD-6. Proxy-path подавляет слишком широкие исключения без диагностики

- **Файл:** `app/ttydproxy/proxy.py:68-97,191-192,195-227,299-306`
- **Риск / трудоёмкость:** средний / M
- **Факт:** HTML injection на любой ошибке возвращает исходные байты,
  `tunnel_sockets()` на любой `Exception` молча завершается, WebSocket handshake
  также имеет `except Exception: pass`, а `conn.close()` глотает всё. Для HTTP
  connect ошибки логируются и превращаются в 502, то есть политика внутри одного
  модуля различается.
- **Последствие:** ошибки протокола и программные дефекты выглядят как обычное
  закрытие вкладки; по логам нельзя отделить client disconnect от regression.
- **Рекомендация:** ловить ожидаемые socket/decode исключения отдельно, логировать
  неожиданные с route/terminal context и ввести единый helper для upstream errors.
  Не логировать cookies или другие request secrets.

### TD-7. Крупные shell-команды содержат несколько самостоятельных Python-программ

- **Файлы:** `bin/claude-auth-snapshot.sh:61-403,415-539`,
  `bin/claude-auth-snapshot-host.sh:68-215`,
  `bin/clihost-billing.sh:83-241,264-341`
- **Риск / трудоёмкость:** средний / M
- **Факт:** JSON parsing, filesystem inspection, diff/verdict и billing collection
  живут в heredoc-блоках Python внутри shell. Billing уже имеет отдельный
  `bin/clihost_billing_lib.py`, но построение sample остаётся во встроенной
  программе; snapshot содержит две такие программы и дублирующий host wrapper.
- **Последствие:** функции нельзя импортировать и тестировать изолированно;
  статический анализ Python не видит их как `.py`, а изменение shell quoting/env
  transport связано с изменением бизнес-логики.
- **Рекомендация:** оставить shell тонким CLI/Docker orchestration wrapper, а
  snapshot build/diff и billing sample build перенести в importable stdlib-only
  Python modules. Сохранить JSON schema golden tests перед переносом.

### TD-8. `AGENTS.md` описывает устаревший основной сценарий

- **Файлы:** `AGENTS.md:3-18,25-32`, `.env.example:36-43,95-100`,
  `entrypoint.sh:501-582`, `Dockerfile:289`
- **Риск / трудоёмкость:** средний / S
- **Факт:** документ говорит, что образ запускает hapi runner и что
  `CLI_API_TOKEN`/`HAPI_API_URL` требуется заполнить, но runner по умолчанию
  выключен и hapi может вообще отсутствовать. Run-команда публикует `3006:3006`,
  хотя web proxy слушает/экспортирует 8080. Указанный `volume/hapi/` отсутствует в
  репозитории. В тестовых командах также не указан обязательный по `CLAUDE.md` и
  CI отдельный `npm test`.
- **Последствие:** новый разработчик получает неработающий web URL и может решить,
  что optional hapi credentials обязательны; локальная проверка пропускает JS
  regressions.
- **Рекомендация:** синхронизировать overview и команды с headless default,
  `8080:8080`, реальным способом создания volume-dir и полным test matrix.

### TD-9. Docker `CMD` не участвует в запуске

- **Файлы:** `Dockerfile:291-296`, `entrypoint.sh:584-586`
- **Риск / трудоёмкость:** низкий / S
- **Факт:** Dockerfile задаёт `CMD ["/usr/sbin/sshd", "-D", "-e"]`, но
  entrypoint не использует `"$@"` и в конце повторно hardcode-ит ту же команду.
  Поэтому override `docker run IMAGE <command>` игнорируется.
- **Последствие:** две декларации могут разойтись; стандартная Docker-точка
  расширения выглядит рабочей, но является мёртвой.
- **Рекомендация:** либо `exec "$@"` с текущим CMD как default, либо удалить CMD и
  явно документировать, что entrypoint всегда запускает sshd.

### TD-10. В корне хранятся устаревшие артефакты

- **Файлы:** `.DS_Store`, `PLAN_TAB_FIX.md:1-80`
- **Риск / трудоёмкость:** низкий / S
- **Факт:** macOS metadata отслеживается git. План Tab ссылается на старый
  монолитный `app/ttyd_proxy.py` и номера строк/подход, которые уже заменены
  package-модулями и тестируемыми assets.
- **Последствие:** шум в репозитории и ложная архитектурная подсказка.
- **Рекомендация:** удалить `.DS_Store`, добавить глобальный ignore-паттерн и
  удалить либо перенести план в архив с явной пометкой «исторический».

## Проверенные области без новой приоритетной находки

- Symlink-safe upload создаёт файлы через directory fd + `O_NOFOLLOW|O_EXCL`;
  возвращать старую TOCTOU-находку по cleanup без нового воспроизводимого
  сценария не следует.
- Relay URL делегирован общему Python builder; прежнего bash-дубля парсинга нет.
- Cookie/auth headers не пересылаются в ttyd, WebSocket sockets включают keepalive,
  а reaper терминалов запускается в фоне — исправления предыдущего аудита
  присутствуют.
- `cli-packages.txt` остаётся единым источником npm install-списка, и CI запускает
  Python, JS и Docker smoke проверки.
